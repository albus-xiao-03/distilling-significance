## 0. Conceptual correction

### 0.1 Definition (owner)

> **Significance** = whether a human would choose to pay attention to an observation and use it for further analysis.

- Significance is a **human decision recorded in the data**: the ground truth. It is not computed from model outputs.
- **The task:** predict that decision for new observations from **(a) the sequence of observations the person encountered** and **(b) their previous decisions**, using BehaviorGPT's existing next-action prediction, **without fine-tuning**.
- BehaviorGPT's predicted decisions are the **pseudo-labels** of the supervised-learning dataset.

### 0.2 What significance is not (owner)

- personalised purchase likelihood;
- behavioural relevance;
- prediction surprise;
- the difference between history-conditioned and unconditional scores (`lift > 0`).

None of these is used as a label anywhere in this plan.

### 0.3 What changed from revision 6

| Aspect | Revisions 4–6 | Revision 7 |
|---|---|---|
| What significance is | Defined by BehaviorGPT's output: lift of history-conditioned over unconditional scores | The person's attention decision, recorded in the data |
| BehaviorGPT's role | Defined the label | **Predicts** the person's decision, as its next action |
| Data needed | Any purchase sequence | Observations **presented** to a person, **which ones they attended**, and their **earlier decisions** |
| Dataset | Amazon Reviews 2023 (Video_Games, Software) | **MIND-small** recommended (N1) |
| Representation | Purchases as `View`/`Order`; low-rated purchases left out | Presented observations and attention decisions written as BehaviorGPT events (§5) |
| Labels | `lift > 0` | BehaviorGPT's predicted attention decision for each presented observation |
| Evaluation | Label profile, stability, association with ratings | Accuracy against the **real** attention decisions; baselines; representation comparison; distillation |
| Removed | — | Lift, z-scores, reference-sample statistics, cold-start lift, rating-aware variant R3, cart variant R5, rating association E4, decision D14 |

### 0.4 Why the dataset has to change

Amazon Reviews 2023 rows record only what a customer **bought and reviewed**. Nothing records observations the customer saw and decided not to pursue, so there is no attention decision to predict or to check predictions against.

Its helpful votes come closest to "attention", but they don't fit either:
- they are anonymous aggregate counts;
- they are biased by exposure (older and top-sorted reviews collect more votes);
- they carry no per-person previous decisions;
- they need the raw review text, which D15 excludes.

## 1. Goal and hypothesis

**Goal.**
1. Take MIND-small, an open log of consumers' news reading.
2. Reorganise it into **decision episodes**: the observations presented to a person (headlines in one impression), which of them the person chose to open, and that person's earlier episodes.
3. Write the episodes in BehaviorGPT's input format.
4. Have BehaviorGPT, unchanged, predict the person's attention decisions for **new** observations.
5. Store those predictions as pseudo-labels: item identifiers and labels only.
6. Measure them against the real decisions.
7. Test whether a small supervised student trained on them recovers the quality of one trained on real decisions ("distilling significance").

**Hypothesis.** An attention decision is a next action: the person acts on one of the observations in front of them. If the representation makes "attending to an observation" the same thing as "acting on it next", and puts the person's earlier observations and decisions in the history, then BehaviorGPT's next-action ranking over the presented observations predicts which ones the person attends to. It should do this better than chance and simple baselines, with no training.

**What would count as a result.** Either outcome is reportable:
- *Positive:* predictions beat chance and baselines, a representation effect shows, and the student recovers a meaningful share of the real-label student's quality.
- *Negative:* we report where the representation or the API stops BehaviorGPT from predicting attention, using §4.

## 4. Limits that prevent direct attention-decision prediction through the existing API

| # | Limitation | Evidence | Consequence for the plan |
|---|---|---|---|
| **L1** | **The API answers "which item comes next", never "will this observation be attended".** | `complete` returns catalog items ranked by score | An attention decision can only be expressed as a **choice among the presented observations**. BehaviorGPT cannot give a yes/no for one observation in isolation. |
| **L2** | **Scores are ranking scores, not probabilities, and compare only within one history.** | "The API returns ranking scores, not probabilities" (anomaly README) | No absolute threshold. Decisions are made within each episode; confidence is rank-based. |
| **L3** | **There is no "stop" or "attend to nothing" action.** The model always ranks something next. | Output is always a ranking | **How many** observations get attention can't come from BehaviorGPT. The plan takes it from the person's previous decisions (§6.3, N5). |
| **L4** | **There is no event for "presented but not attended".** | Vocabulary `Search`/`View`/`Order`; "any sign of interest counts as a view"; `AddToCart` reads as `View`; `RemoveFromCart` "does not change results" (SDK) | A dismissal can only be expressed by leaving the observation out (V1) or as a `View` left out of the `Order` (V2, V3). An explicit negative event doesn't exist. |
| **L5** | **The presented set is not a model input.** The `id` filter only selects which scores come back. | §3.1 | In V1/V2 BehaviorGPT doesn't know what else was on screen. Only V3 writes the screen into the history. |
| **L6** | **Only two prediction questions:** next item viewed, or "what else goes in the same purchase". There's no "which of the viewed items will be ordered". | SDK `complete` docstring; README | V3 depends on `predict="purchase"` scoring the session's **own** viewed items. **Phase 0 probe; if they are suppressed, V3 is dropped.** |
| **L7** | **Items already in the history are ranked low on purpose.** | anomaly README §2 | An observation is never in its own scoring context. In V2/V3, an observation re-presented after being ignored earlier is suppressed (reported separately). Repeated generic "decision" items would also be suppressed, which is why decision-item encodings aren't used (§12). |
| **L8** | **Items are read from their content only** (name, brand, categories, image; price display-only). | `docs/catalog-format.md` | Attention drivers outside the text (screen position, freshness, time of day) are invisible. MIND shuffles impression order, so position is unavailable anyway. |
| **L9** | **Real timing is lost.** | SDK re-stamps history events; `complete` doesn't expose the request `timestamp` (**SDK-only**) | Time gaps between decisions and the episode's time of day aren't used |
| **L10** | **Call shape:** ≤ 100 ids per call; history length and rate limits undocumented | §3.2 | Large impressions are chunked (same history, same scale). History is capped at the measured maximum (*K*). |
| **L11** | **Every observation must be a catalog item uploaded to Unbox AI** (≤ 100k per catalog, 2 per key) | `docs/catalogs.md` | MIND headlines must be uploaded (N3); MIND-small only. |
| **L12** | **Pretraining domain:** retail, engagement, payments | SDK README | Headlines are engagement-like but not products; results may not transfer to professional analysis settings |

**Net effect:**
- **Possible directly:** BehaviorGPT can rank the presented observations by which the person will act on next, given their earlier observations and decisions. That ranking is the attention prediction itself.
- **Not possible directly:** a per-observation yes/no, the **number** of observations attended (L1, L3), and an explicit "not attended" event (L4). The plan handles these with an in-episode decision rule driven by the person's own previous decisions (§6), and states it as a limitation.

## 5. Representation: observations and attention decisions as BehaviorGPT events

### 5.1 Mapping

| In the data | In BehaviorGPT |
|---|---|
| Observation: a headline shown in an impression | A **catalog item** (§5.2) |
| Decision episode: one impression | One **session** |
| Attention decision "attend" (click) | The person's **action on the observation**: `View` (V1) or `View` + `Order` (V1o, V2, V3) |
| Decision "not attend" | **Left out** (V1, V1o), or a `View` **left out of the `Order`** (V2, V3), the SDK's documented way |
| Previous decisions | Earlier sessions, oldest first. The `History` clicks (no presented sets) form the first session, then each earlier impression of the same person. |
| New observations to decide on | The current impression's presented set: the **candidates for the next action** |

|---|---|---|
| `id` | News ID | |

| `brand` | null | |
| `categories` | `"<Category>, <SubCategory>"` | |
| `keywords` / `search_keywords` | Entity labels / surface forms | |
| `image_url` | null | Text-only (allowed) |
| `event_type`, `group` | `"product"` | Required |
| `market` | `"US"` | |
| `sales_since`, `timestamp`, `frequency`, `price` | null | No popularity prior baked in |

### 5.4 Representation variants (the central experiment)

| Variant | History sent to BehaviorGPT | Question asked | What it tests |
|---|---|---|---|
| **V1** attention as next view | Attended observations as `View`, one session per earlier episode | `predict="view"`, restricted to the presented observations | Previous decisions only (the native "a read is a view") |
| **V1o** attention as commitment | Attended observations as `View` + `Order` | Same | Does an explicit decision event help? |
| **V2** observations and decisions | Each earlier episode: `View` every presented observation, then `Order` the attended ones; not attended = left out of the `Order` | `predict="view"`, restricted to the presented observations (not written into the history) | Adds the **observation sequence**, so the person's ignored observations are seen |
| **V3** decide on what is on screen | V2's history, plus the current presented observations as `View`s in the current session (seeded order) | `predict="purchase"`, restricted to the presented observations | Adds the **screen** itself. **Phase 0 go/no-go** (L6). |

**Rules for every variant:**
- Strictly earlier episodes only.
- No candidate appears in its own scoring history, except V3's current session, which is the point of V3 and is checked in Phase 0.
- History capped at *K* events, keeping the most recent sessions whole.
- Same-catalog ids only.

## 6. Predicting the decisions (the pseudo-labels)

### 6.1 Calls

```
complete(H, limit=len(P), filters={"id": P}, catalog_id=<MIND catalog>, predict=<"view" | "purchase">)
```

`P` = presented observations not yet decided. Up to 100 per call; chunks share `H`, so they share one scale. Every call carries no `user_id`, is cached in SQLite under `.temp/cache/`, is retried on 429/5xx, and is throttled to the Phase 0 limit.

### 6.2 Next-action decoding: BehaviorGPT acts as the person

For V1, V1o and V2:
1. Score the presented observations given `H`. The top one is BehaviorGPT's predicted next action, so it is **attended**.
2. Append that attention event (`View`, or `View` + `Order`) to the current session and re-score the rest.
3. Repeat until *k* observations are attended (§6.3). The rest are **not attended**.

For V3: one `predict="purchase"` ranking; the top *k* are attended.

Every observation gets `attention_rank`, the step at which BehaviorGPT chose it (unchosen ones are ordered by their final scores).

### 6.3 How many observations get attention (*k*): limitation L3

- *k* = max(1, round(*a* × *n*)), where *n* is the number of observations presented in the episode and *a* is **the person's own attention rate in their earlier episodes** (share of presented observations they clicked). This uses only previous decisions, never the episode being predicted.
- **No earlier episodes:** *k* = 1. Every MIND impression is expected to contain at least one click; this is checked in Phase 1.
- **Diagnostic only:** "oracle *k*" (the true number of clicks) separates ranking errors from count errors. It is never used for the labels.

### 6.4 Per-observation outputs

- `predicted_attention`: 1 / 0;
- `attention_rank`: 1 = BehaviorGPT's first predicted action;
- `confidence` = 1 − (`attention_rank` − 1) / *n* (rank-based, because of L2).

### 6.5 Choosing the representation (D16)

1. V1, V1o, V2 (and V3 if Phase 0 allows) run on **1,000 selection records**: impressions from the last day of MIND's *training* file. They are separate from the 5,000 evaluation records (MIND's *validation* file), so the choice never sees evaluation data.
2. The variant with the best AUC against those records' real decisions is chosen.
3. Only the chosen variant runs on the 5,000 records.

## 8. Evaluation: against the real human decisions

| # | Question | Measure |
|---|---|---|
| **E1** | How well does BehaviorGPT rank the presented observations by attention? | Per-record AUC, MRR, nDCG@5/@10 (MIND's standard metrics) of `attention_rank` against real clicks |
| **E2** | How good are the pseudo-labels as decisions? | Precision, recall, F1, accuracy, Cohen's κ against real decisions; error in *k*; the oracle-*k* diagnostic |
| **E3** | What does each input contribute? | **(a) Previous decisions:** the same predictor with an empty history vs V1. **(b) The observation sequence:** V2/V3 vs V1. **(c) The decision event:** V1o vs V1. |
| **E4** | Distillation: does a supervised student trained on the pseudo-labels learn the real decisions? | Logistic regression on non-BehaviorGPT features: title TF-IDF, category, subcategory, the person's past attention share per category, the observation's earlier click rate, history length, episode size. Trained on pseudo-labels of 80 % of records (split by person), evaluated on **real** decisions of the other 20 %. Compared with the same student trained on real decisions (upper bound), on popularity labels, and on random labels. **Recovery** = (AUC_pseudo − 0.5) / (AUC_real − 0.5). |

**Baselines (no BehaviorGPT), all using the same *k* rule for decision metrics:**
- random;
- **popularity**: the observation's click rate in impressions strictly before the record (strong on news);
- recency: when the observation first appeared;
- **content similarity**: TF-IDF cosine between the observation's title and the person's previously attended titles.

All measures come with **95 % bootstrap CIs** over persons. Only aggregates are reported.

**Success targets:**
1. 5,000 records predicted end to end, cached and reproducible.
2. The chosen variant beats random, with the CI excluding AUC 0.5. It is compared with popularity; beating popularity is a stretch.
3. E3 is reported in whichever direction.
4. Recovery ≥ 50 % (a target).

## 11. Risks and mitigations

| Risk | Effect | Mitigation |
|---|---|---|
| BehaviorGPT's next-action ranking barely tracks attention on headlines (L12) | Weak pseudo-labels | Baselines and E3 show where it fails; a negative result is reportable |
| V3 impossible (L6) | One fewer representation | Phase 0 probe; V1, V1o, V2 still answer the core question |
| The *k* rule, not the ranking, dominates errors (L3) | Misleading decision metrics | Oracle-*k* diagnostic; E1 ranks independently of *k* |
| Re-presented observations suppressed in V2/V3 (L7) | Biased V2/V3 scores | Report that subset separately |
| History too long for the API (L10) | Lost earlier decisions | Phase 0 measures *K*; keep the most recent sessions |
| MIND licence and upload (N3) | Licence exposure | Private catalog; deletion term and command; no data in the repo or pushes |
| Rate limits | Slow run | Phase 0 measurement; throttle; cache + resume (~21k calls) |
| Leakage | Inflated results | Previous decisions strictly earlier; selection records separate from evaluation records; popularity only from earlier impressions; no popularity in the catalog |
| Re-identification from the output | Licence / privacy | Output has no person, time or history fields; the schema test enforces it |
