## 1. Goal and hypothesis

**Goal.** Build a pipeline that:

1. takes open datasets of real people's behaviour;
2. rewrites them as **sequences of observations and the human decisions about whether each one deserved further attention**, in BehaviorGPT's own input format;
3. asks BehaviorGPT, **unchanged (no fine-tuning, no retraining)**, to predict that decision for new observations;
4. turns those predictions into **pseudo-labels**, giving a supervised-learning dataset;
5. measures how good the pseudo-labels are against the real decisions, and how much of a gold-trained classifier's quality a classifier trained on them recovers ("distilling significance").

**Hypothesis.** BehaviorGPT predicts what a person acts on next. If "this observation deserves further analysis" is written as **the person choosing that observation**, then its pretrained next-choice ranking is a zero-shot significance scorer. How the sequence is represented (what counts as a choice, how sessions and dismissals are encoded) changes how good that scorer is. That representation effect is the experiment.

**What would count as a result.** Either outcome is reportable:
- *Positive:* zero-shot pseudo-labels clearly beat chance and simple baselines, and a student trained on them recovers a meaningful share of the gold-trained student's quality.
- *Negative:* the representation does not carry the signal. We report which variants failed and by how much.

## 4. Core idea: significance is a choice

BehaviorGPT can only say one thing: *"given what this person did, how likely are they to act on item X next?"* Everything else is representation. The design follows three rules:

1. **"Deserves further analysis" = the person chooses the observation.** This is the model's native positive action. A flagged observation becomes a choice event (`View`, or `View` + `Order` in some variants).
2. **"Dismissed" is never a `View` in the person's own history.** The model reads any view as interest (README "Events"), so dismissals appear only by being left out (llms.txt principle 6), as **candidates to score**, or in a separate contrast context (variant R3).
3. **Never score an observation from a history that already contains it.** Seen items are pushed down on purpose (anomaly README §2), which would bias every score.

A fourth signal comes from the anomaly example: **surprise**. An observation the model did not expect, given the history, may be exactly what deserves a second look (Track B2).

## 5. Significance Sequence Format (SSF)

A dataset-agnostic format. Each dataset gets one small adapter that writes **(i) a new catalog parquet** and **(ii) SSF episodes**.

### 5.1 Record shape

```jsonc
// ILLUSTRATIVE ids/values. One SSF record = one "triage episode": a person, their past decisions, and new observations to decide on
{
  "episode_id": "dev-91",                // MIND impression id
  "subject_id": "U397059",               // the person making decisions
  "time": "2019-11-15T10:22:32",
  "context": {
    "flagged":   [["N106403", "N71977"], ["N97080"]],   // sessions of past observations they chose, oldest first
    "dismissed": [["N5521", "N7781", "N9003"]]          // observations they were shown earlier and passed over
  },
  "candidates": ["N129416", "N26703", "N120089", "N53018"],  // new observations needing a decision
  "gold": {"N26703": 1, "N120089": 1, "N129416": 0, "N53018": 0}  // real decisions; NEVER sent to BehaviorGPT
}
```

Gold labels are stored separately from what the teacher reads, so leakage is structurally impossible. **Every SSF file and catalog parquet is dataset-derived, kept git-ignored and never committed.**

Embedded with `reference_time` = the test cut-off t₂.

**Episodes:** from the `5core/timestamp` split, which uses the McAuley Lab's global cut-offs (t₁ = 1628643414042, t₂ = 1658002729837 ms; verified), so train, valid and test never overlap in time.

These are real human decisions with real negatives. The question is whether BehaviorGPT's **surprise** at a purchase, given what the customer bought before, predicts that it disappointed.

## 6. Zero-shot teacher

### 6.1 Scoring

For an episode with history `H` and candidates `c₁…cₙ`:

```
s(c | H) = score of c from client.complete(H, limit=len(chunk), filters={"id": chunk}, catalog_id=<track catalog>)
```

Candidates are sent in chunks of ≤ 100 ids. Every call:
- is cached on disk by (catalog name + content hash, history, ids), in SQLite under `.temp/cache/`, so results survive a catalog being deleted and re-created (§9.3);
- is retried with backoff on 429/5xx;
- carries **no `user_id`**, so nothing is recorded on the account.

The prior `s(c | ∅)` (empty history) is cached once per item. Because we built each catalog, the **complete item list is known**, so uniform reference samples cover the whole catalog. (`behaviorgpt-anomaly` had to snapshot `retail_catalog` through rankings instead.)

### 6.2 Representation variants (the core experiment)

| Id | History sent to BehaviorGPT | What it tests | Tracks |
|---|---|---|---|
| **R0** native | All flagged observations as `View`s, one session, oldest first | The plain "a read is a view" mapping (baseline representation) | A, B |
| **R1** explicit decision | Each flagged observation as `View` then `Order` | Does encoding "flagged" as a *choice* (not just a look) sharpen the signal? | A, B |
| **R2** triage sessions | R1, but split into sessions: one per earlier decision episode or day, plus the old history as the first session | Does episode structure help? *(multi-session histories are SDK-only)* | A, B |
| **R3** contrastive dismissal | `s(c│H_flagged) − λ·s(c│H_dismissed)`, with dismissed observations as `View`s in a **separate** context; λ = 1 (no tuning) | Can "what they passed over" be used without the model reading it as interest? | A |
| **R4** prior-normalised | `s(c│H) − s(c│∅)` (a pointwise-mutual-information-style score); combinable with R3 | Removes "everyone picks this" popularity, leaving what is specific to the person | A, B |
| *R5 (optional)* explicit rejection | Dismissed observations as `AddToCart` → `RemoveFromCart` inside R2's sessions | Whether a "considered, then rejected" funnel encodes dismissal. **SDK-only events; ablation only.** | A |

History length is capped at the last *K* events (K = 50 by default, adjusted after the Phase 0 measurement). **Catalog-side ablations** (title vs. title + abstract; with or without train-window popularity) are run by refreshing the track's catalog under the same file name.

### 6.3 From scores to pseudo-labels

Raw scores are on a per-history scale (not probabilities), so labels are assigned by **rank within an episode**:

- **P1, zero-gold (main):**
  - the top *k* candidates per episode → `1`, with *k* = 1 (MIND impressions contain at least one click; verified on data in Phase 1, else *k* = max(1, …));
  - the bottom 50 % → `0`;
  - the rest → **abstain** (no label);
  - `confidence` = the rank margin.
- **P2, few-shot calibration (ablation, clearly labelled):** a gold *seed* of ≤ 5 % of episodes fits a 1-D logistic calibration and a base-rate threshold. BehaviorGPT is still untouched; only this downstream mapping sees gold.

### 6.4 Track B1 teacher

R0/R1/R2/R4 over the B1 candidate sets, with labels as in P1.

### 6.5 Track B2 teacher (surprise)

For each purchase `o` with earlier history `H`, with no gold anywhere:
- `s(o│H)`;
- the PMI score `s(o│H) − s(o│∅)`;
- `o`'s rank against a fixed uniform sample of the **full** Track B catalog, the method of `behaviorgpt-anomaly` `scoring.py`.

Significance score = **−PMI**: the less expected the purchase, the more it deserves follow-up. Pseudo-labels are the top *q* % most surprising per customer-month → `1`, the bottom 50 % → `0`, the rest abstain; *q* is set from the train-window base rate in P2 only.

## 8. Evaluation

### 8.1 Teacher quality against real decisions

- **Track A (MIND dev split):** AUC (mean per episode), MRR, nDCG@5/@10 (MIND's standard set); for binary pseudo-labels, precision/recall/F1, Cohen's κ against gold, and coverage vs. accuracy as the abstention band widens.
- **Track B1:** hit-rate@k, MRR and AUC, under uniform and popularity-matched negatives.
- **Track B2:** AUC and average precision of surprise against `rating ≤ 2`, with its base rate reported alongside.
- **All tracks:** **95 % bootstrap CIs** over episodes (or customers).
- **Baselines (no BehaviorGPT):**
  - random;
  - popularity (from strictly earlier data);
  - recency (A);
  - TF-IDF similarity between the candidate's title and the person's earlier titles (A, B1);
  - item-level train-window rate of `rating ≤ 2` (B2).

  Popularity is known to be strong on news, so beating it is a stretch target, not a requirement.

### 8.2 Distillation (the "supervised dataset" payoff)

The **student** is a scikit-learn logistic regression on features that don't use BehaviorGPT:
- TF-IDF of the title;
- category one-hots;
- the person's past share of choices in that category;
- prior popularity;
- history length and episode size;
- price (B).

| Student trained on | Role |
|---|---|
| Gold labels (train split) | Upper bound |
| **BehaviorGPT pseudo-labels (train split, gold hidden)** | **The result** |
| Popularity-heuristic labels | Simple-teacher comparison |
| Random labels | Floor |

All students are evaluated on the **gold** evaluation split of their track.

**Headline number:** recovery = (AUC_pseudo − 0.5) / (AUC_gold − 0.5). Run for Track A, and for Track B2 if its teacher beats chance.

### 8.3 Hackathon success targets

1. **End to end:** the pipeline runs on ≥ 1,000 evaluation episodes per track, fully cached and reproducible.
2. **Above chance:** in Track A, and in at least one Track B label set, the best zero-shot variant beats random with a 95 % CI that excludes AUC 0.5.
3. **Representation effect:** at least one of R1–R4 differs from R0 beyond its CI. Reported in whichever direction it goes.
4. **Distillation:** report recovery. Target ≥ 50 % on Track A.
5. **Track B2:** reported with its baseline. Exploratory; no target.

### 9.3 Catalog slot strategy (the 2-per-key limit never blocks the plan)

The project needs one new catalog per track (two in total), plus optional same-name refreshes for ablations, which use no extra slot. Phase 0's `list_catalogs()` decides which case applies:

1. **Two free slots:** embed both catalogs.
2. **Fewer free slots** (e.g. the key already holds catalogs such as `cat_55125…`), in order of preference:
   1. **Ask Unbox AI for more slots** (`admin@unboxai.com`, per `docs/catalogs.md`). The owner sends the request at Phase 0.
   2. **Time-share one slot:** embed Track A → run all its scoring (cached) → `delete_catalog` → embed Track B → score. The cache is keyed by catalog content, not id, so finished work survives the swap. Re-scoring later means re-embedding (minutes).
   3. **Delete an existing catalog** only with the owner's **explicit** permission for that specific catalog (irreversible).

## 11. Risks and mitigations

| Risk | Effect | Mitigation |
|---|---|---|
| Headlines are far from the retail items the model saw most | Weak Track A signal | R0–R4 and the TF-IDF baseline make it measurable; a title+abstract ablation; Track B is native retail; a negative result is still a result |
| **Licensed data leaks into the public repo** | Licence breach | `outputs/` and `.temp/` git-ignored; tests use synthetic fixtures; reports are aggregates only; `git status`/diff reviewed before every commit; never push without permission |
| **Access approvals and the MIND gate** | Phases 0–4 blocked | D8 owner actions listed; Phase 0 starts only after them |
| MIND upload to a third party (Unbox AI) | Licence ambiguity | D9 owner decision; private catalog; delete after the hackathon |
| **Catalog slots (2 per key)** | Can't hold both tracks at once | §9.3: ask for more slots, else time-share with a content-keyed cache; never delete without explicit permission |
| Amazon image URLs not fetchable by Unbox's servers | Embed job fails | ~300-row slice first; if images fail, embed text-only (title + store + categories), which the docs allow |
| Video_Games 5-core has > 100k items (unlikely: 137.2K in the whole category) | Doesn't fit one catalog | Keep the most-reviewed train-window items, plus every item in an evaluation episode; or Software (D11) |
| Track B1 negatives are sampled, not human-shown | Optimistic B1 numbers | Two schemes (uniform, popularity-matched); reported as the weaker label; B2 uses real negatives |
| Raw scores aren't probabilities and differ per history | Mis-calibrated labels | Rank-within-episode labelling (P1); PMI normalisation (R4); optional P2 calibration |
| Seen-item suppression | Biased scores | Rule 3 of §4: candidates are never in their own scoring history |
| Dismissals read as interest | Inverted signal | Rule 2 of §4; dismissals only in R3's separate context or the R5 ablation |
| Undocumented rate limits and history length | Stalls, refusals | Phase 0 measurement; cache; throttle; cap history at K |
| History timing is synthetic (SDK re-stamps events) | Time features lost | Accepted. Order is preserved, which is what the variants test. |
| Leakage | Inflated results | Gold kept out of SSF context; popularity only from strictly earlier data; MIND's own time split; Amazon's global timestamp split; catalogs' `reference_time` at the cut-off |
