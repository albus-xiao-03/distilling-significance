## 1. Goal and hypothesis

**Goal.** Take an open **customer-behaviour** dataset (Amazon Reviews 2023) and do the following:

1. reorganise it as **behavioural sequences**: each customer's observations (products they engaged with) and their decisions (buying, then rating), in BehaviorGPT's input format;
2. let BehaviorGPT, **unchanged (no fine-tuning, no retraining)**, **decide how significant each observation is** for that person, from what they did before;
3. publish locally a **significance-labelled dataset** containing **only item identifiers and the labels BehaviorGPT produced**;
4. check that BehaviorGPT predicts this domain's behaviour, characterise the labels, and test whether a small supervised student can learn them ("distilling significance").

This is done for **two category versions**, Video_Games and Software, so the result is not tied to one domain.

**What "significance" means here.** We do **not** define it. BehaviorGPT's job is predicting what a person acts on next. The significance of an observation is **how much this person's history raises BehaviorGPT's expectation of them acting on it, compared with no history**. Both the score and the yes/no decision come from the model's own outputs, with no thresholds tuned on human labels (§6).

**Hypothesis.** A pretrained behaviour model, given a suitable representation of a person's sequence, yields a consistent and informative significance signal with no task-specific training. How the sequence is represented changes that signal; this is the representation experiment.

**What would count as a result.** Either outcome is reportable:
- *Positive:* BehaviorGPT predicts held-out behaviour above baselines, the labels are stable and informative, and a cheap student reproduces them in both categories.
- *Negative:* any of these fails. We report where and by how much.

## 4. Core idea: let BehaviorGPT decide significance

1. **The human decisions are already in the data.** A purchase is a choice; a rating is the customer's verdict. The sequence is written so BehaviorGPT reads these decisions (§5.2).
2. **The significance of an observation is BehaviorGPT's expectation of the person acting on it, given their history, relative to no history.** This separates "important to *this* person" from "popular with everyone".
3. **The model also makes the decision:** an observation is significant when the person's history raises it (`lift > 0`), with no tuned threshold (D14).
4. **Never score an observation from a history that already contains it.** 5-core has no repeated user–item pairs, so each observation is scored on the strictly earlier history.

## 5. Representation

### 5.1 New catalogs: one per category (two in total, both slots)

All `parent_asin` in the category's 5-core split, one row each, built from its metadata file. The catalog covers the **whole** 5-core item set, not just the 5,000 records, so BehaviorGPT ranks against the full product space.

| Catalog column | Value | Note |
|---|---|---|
| `id` | `parent_asin` | |
| `name` | `title` | |
| `brand` | `store` (else `details.brand`) | |
| `categories` | `categories` joined `", "` (else `main_category`) | |
| `image_url` | First `images[].large` (`https://m.media-amazon.com/…`) | A ~300-row slice is embedded first |
| `price`, `currency` | `str(price)` or null, `"USD"` | Display only |
| `market` | `"US"` | |
| `event_type`, `group` | `"product"` | Required |
| `sales_since`, `timestamp`, `frequency` | null | No popularity prior baked in |

Embedded with `reference_time` = t₂.

**Note on D15:** BehaviorGPT reads items from their content, so the catalog necessarily holds item content (title, store, categories, image link) **inside Unbox AI under this key**. That is processing, not the output dataset. These catalogs are covered by the deletion term (§7.3).

If a category's 5-core item set exceeds 100k (not expected: 137.2K items in all of Video_Games), that catalog keeps the items of the sampled sequences, the reference sample, and the most-reviewed train-window items up to 100k.

### 5.2 Record selection (D17: 5,000 per category)

- **Seeded customer sampling:** whole customers are drawn at random until their reviews reach **~5,000 records**. Every record of a sampled customer is labelled, so each record has its true earlier history.
- **Test-window coverage:** sampling is stratified so that **≥ 1,000 records fall in the test window** (after t₂), for evaluation E1/E5.
- **Variant subset:** a fixed **1,000-record subset** (whole customers) of the 5,000 is used for the representation comparison (D16).

### 5.3 Sequences (Significance Sequence Format, SSF)

One sequence per sampled customer, ordered by time:
- **observations** = the products they reviewed (a purchase proxy);
- **decisions** = buying them, and the rating they gave.

Same-day purchases form one session. Every observation is scored from the history **strictly before its session**, capped at the last *K* events (K = 50, adjusted in Phase 0). SSF files are local and git-ignored.

| Variant | How the history is written | What it tests |
|---|---|---|
| **R0** native | Earlier purchases as `View`, one session | The plainest mapping |
| **R1** choice | Earlier purchases as `View` + `Order` | Does encoding the decision as an order sharpen the signal? |
| **R2** sessions | R1, one session per day (**SDK-only** multi-session) | Does session structure matter? |
| **R3** verdict-aware | R2, but purchases the customer rated ≤ 2 are **left out** of later histories ("taking a step back", llms.txt principle 6) | Does respecting the customer's own verdict change significance? *(The rating is used only as recorded history, never as a target, and never stored in the output.)* |
| *R5 (optional)* | R2, with low-rated purchases as `AddToCart` → `RemoveFromCart` (**SDK-only**) | Alternative encoding of a rejected purchase |

## 6. Significance computation (model-native)

### 6.1 One call per customer-session

For a session with observations `O` (≤ 10 per call) and history `H`:

```
complete(H, limit=len(O)+len(R), filters={"id": O ∪ R}, catalog_id=<category catalog>)
```

`R` is a **fixed uniform reference sample** of ~90 items from the category's full item list (known because we built the catalog). Reference items present in `H` are dropped for that call.

- **Prior scores:** `s(·│∅)` once per item needed (the records' items and `R`).
- **Every call is:**
  - cached in SQLite under `.temp/cache/` (resumable);
  - retried with backoff on 429/5xx;
  - throttled to the limit measured in Phase 0;
  - sent without `user_id`, so nothing is recorded on the account.

### 6.2 Computed fields

| Field | Meaning | In the output? |
|---|---|---|
| `z_hist` | Robust z-score (median/MAD) of `s(o│H)` against `R` under the same `H` | Local only |
| `z_prior` | The same with no history | Local only |
| **`significance`** | **`lift = z_hist − z_prior`**: how much this person's history raises `o`, judged by BehaviorGPT | **Yes** (main outcome) |
| **`significant`** | **`lift > 0`** (D14); null for cold start | **Yes** |
| `confidence` | `|lift|` scaled by the reference spread | **Yes** |
| `cold_start` | First session of a customer (empty history) | **Yes** (label metadata) |

### 6.3 Why this decision rule (D14)

- It uses only BehaviorGPT outputs.
- It needs no threshold: zero means "the history doesn't change how much the model expects this item".
- It compares like with like: the same reference items and the same model, with and without the person's history.

### 6.4 Choosing the representation (D16)

R0–R3 (R5 optional) run on the **1,000-record subset** per category. The chosen variant then runs on **all 5,000 records**, reusing the subset's cache. The choice criterion is behavioural, not a significance definition: the variant under which BehaviorGPT best predicts customers' **actual next purchases** (E1) on the subset's train/valid windows. Each category may end up with a different variant; both are reported.

## 8. Evaluation (per category)

| # | Question | How | Baselines |
|---|---|---|---|
| **E1** | Does BehaviorGPT do its job here? | For each **test**-window session among the 5,000 records: rank of the actually purchased item, from one extra top-100 head call plus the reference sample; hit@10/@100, MRR, mean percentile | Random; popularity (train-window counts); item-to-item co-occurrence (train window) |
| **E2** | Does the representation matter? | E1 per variant on the 1,000-record subset; agreement of `significant` between variants (Cohen's κ); rank correlation of `significance` | — |
| **E3** | What do the labels look like? | Base rate; distributions; confidence; by split, history length, cold start | — |
| **E4** | How does significance relate to the customers' own signals? (descriptive) | Spearman / AUC of `significance` against `rating`, computed **locally**, reported as aggregates; **never used to tune anything** | — |
| **E5** | Distillation: can a cheap model learn BehaviorGPT's significance? | A logistic regression on non-BehaviorGPT features computed **locally and transiently** from the raw data (title TF-IDF, category, store, price band, past category shares, history length, train-window popularity). Train on train-window labels, select on valid, report on test: AUC and κ against `significant`, R² against `significance`. Features are never written to the output. | Majority class; popularity-only features |

**Cross-category:** the same metrics side by side for Video_Games and Software.

All metrics come with **95 % bootstrap CIs** over customers. Reports are aggregate-only.

**Success targets (per category):**
1. 5,000 records labelled end to end, cached and reproducible.
2. E1: BehaviorGPT beats popularity on next-purchase rank, with the CI excluding a tie.
3. E2: the representation effect is reported in whichever direction.
4. E5: the student reaches AUC ≥ 0.7 against BehaviorGPT's labels (a target).

With ~1,000 test records per category the CIs will be wide; that is accepted under D17.

## 11. Risks and mitigations

| Risk | Effect | Mitigation |
|---|---|---|
| Source-data rights are unknown (D10) | Legal exposure | No source data in the repo or the output (D15); README rights notice and deletion term from Phase 0; deletion command; catalogs deletable; no push without permission |
| Item content sits in Unbox AI catalogs | Data held by a third party | Necessary for BehaviorGPT; private to this key; covered by the deletion term and command |
| Small evaluation sets (D17) | Wide CIs | Bootstrap CIs reported; test-window stratification (≥ 1,000 per category); conclusions stated with their uncertainty |
| Rate limits | Slow run | Phase 0 measurement; throttle; cache + resume (budget is small: ≤ ~18k calls) |
| Amazon images not fetchable by Unbox's servers | Embed job fails | ~300-row slice first; fall back to text-only rows (allowed) |
| A category's 5-core item set > 100k | Doesn't fit one catalog | Cap at 100k, keeping sampled-sequence items, the reference sample and the most-reviewed items (§5.1) |
| Reference-sample noise (~90 items) | Noisy z-scores | Robust statistics; the same `R` everywhere; Phase 0 stability check; a second filtered call if needed |
| Seen-item suppression | Biased scores | Strictly earlier histories; no repeated pairs in 5-core; reference items in `H` dropped |
| Significance mirrors popularity | Uninformative labels | Lift against the no-history prior removes popularity by construction; E3/E4 check it |
| Re-identification from the output | Rights / privacy issue | Output holds no user, time or sequence fields (§7.1); a schema test enforces it |
| Leakage across time | Inflated E1/E5 | Strictly earlier histories; global time split; train-window baselines; no popularity columns in the catalogs |

## 12. Potential further plan: Track A (MIND news)

Kept for a later plan (e.g. R2). Not part of R1.

- **Data:** MIND-small on HF `yjw1029/MIND` (53.0 MB train, 30.9 MB dev). Each impression records every headline shown with click 1/0, plus the reader's click history. Full MIND (~160k articles) exceeds one catalog, so small only.
- **Why it is interesting:** explicit shown-and-passed-over decisions. It would test the same model-decided significance with dismissals available (a separate "passed over" context, contrastive scores).
- **Prerequisites:**
  - accept the Microsoft Research License on HF and add a read-only `HF_TOKEN` (the repo is gated; currently 401);
  - decide on uploading MIND headlines to Unbox AI (the licence forbids distribution and is silent on processing services);
  - a catalog slot (both are used by R1; delete or time-share);
  - the same output and README rules as R1.
- **Reuse:** the R1 pipeline (SSF, significance scorer, deletion command, data card, student) is dataset-agnostic; Track A adds a MIND reader and a text-only catalog adapter.
